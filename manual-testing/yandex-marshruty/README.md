# Тестирование веб-приложения «Яндекс.Маршруты»

Этот проект — моя учебная работа по ручному тестированию. Я проанализировала требования, составила тестовую документацию и проверила работу сервиса.

---

## 🎯 Что тестировалось
**Объект:** Веб-приложение для построения маршрутов (предположительно, с расчетом времени и стоимости).
**Задача:** Проверить функциональность, UI и обработку ошибок на основе предоставленной документации.

---

## 📋 Что было сделано
1.  **Анализ требований** — изучила макет в Figma и описание функционала.
2.  **Декомпозиция требований** — разложила макет и логику на проверяемые элементы, прежде чем писать чек-листы:
    *   **Декомпозиция вёрстки** (Каршеринг / тариф «Роскошный») — по каждому блоку формы бронирования.
    *   **Декомпозиция логики** — поведение полей «Способ оплаты» и «Добавить карту».
3.  **Тест-дизайн** — вывела классы эквивалентности и граничные значения в отдельную таблицу: для каждого класса зафиксированы границы и тестовые данные внутри класса.
4.  **Составление тестовой документации:**
    *   **Чек-лист для вёрстки (Каршеринг / тариф «Роскошный»)** — 61 пункт.
    *   **Чек-лист для функционала (Способ оплаты и Добавление карты)** — 39 пунктов.
    *   **Тест-кейсы для кнопки «Забронировать»** — 5 сценариев с предусловиями и пошаговыми действиями.
5.  **Выполнение тестирования:**
    *   Чек-лист вёрстки прогнан **в двух браузерах и двух разрешениях** — Яндекс.Браузер 800×600 и Firefox 1920×1080, то есть 122 прогона на 61 проверку.
    *   Результат каждой проверки зафиксирован статусом: Passed, Failed, Skipped или Blocked.
    *   **Баг-репорты** — описала все найденные проблемы.


---

## 🔍 Использованные техники тест-дизайна
Для лучшего покрытия я применила:
*   **Классы эквивалентности** — чтобы разбить все возможные входные данные на группы. Разбор вынесен в отдельную таблицу: например, для номера карты выделены классы «меньше 12 символов», «ровно 12» и «больше 12».
*   **Граничные значения** — чтобы проверить поведение системы на границах допустимых значений: для числовых полей зафиксированы границы диапазона и данные по обе стороны от них.
*   **Предугадывание ошибок** — чтобы найти скрытые проблемы, основываясь на типичных ошибках в таких сервисах.

## 📈 Результаты
*   **Всего написано:** 105 тестов (61 чек-лист по вёрстке + 39 чек-листов по функционалу + 5 тест-кейсов).
*   **Найдено багов:** 39.
    *   🔴 **6 блокирующих** — ошибки, которые полностью останавливают работу (например, невозможность завершить бронирование).
    *   🟠 **14 критических** — проблемы с ключевым функционалом (неверный расчёт стоимости, ошибки в логике).
    *   🟡 **4 стандартных** — незначительные баги, не влияющие на основной сценарий.
    *   🟢 **15 желательных** — мелкие недочёты, которые можно исправить в следующих версиях.
*   **Самые частые проблемы:** ошибки валидации полей и некорректное отображение цен при смене тарифа.
